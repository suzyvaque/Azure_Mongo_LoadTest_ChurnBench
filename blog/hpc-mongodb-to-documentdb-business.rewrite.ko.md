# 상품평가 HPC의 데이터 계층을 관리형으로: Azure DocumentDB 도입과 검증

상품평가 HPC 플랫폼에서 중요한 것은 계산 노드의 성능만이 아닙니다. 계산에 필요한 데이터를 제때 전달하고, 요청이 몰릴 때도 작업을 이어갈 수 있어야 합니다. 데이터베이스의 연결 수립과 운영 방식도 전체 처리 흐름에 영향을 줍니다.

Caldova Securities(가명)의 Azure 기반 HPC 플랫폼은 자체 관리형 MongoDB를 Azure DocumentDB로 전환하는 과정에서 이 문제를 검토했습니다. 기존 애플리케이션의 MongoDB 사용 방식을 유지할 수 있는지, task마다 새 연결을 만드는 부하를 처리할 수 있는지, 직접 구성하고 관리하던 범위를 어디까지 서비스에 맡길 수 있는지가 주요 검토 항목이었습니다.

이 글은 운영계로 선정한 **Azure DocumentDB M80·샤드 2개·고가용성(HA) 구성**과 그 판단을 뒷받침한 테스트, 그리고 관리형 서비스에서도 남는 설계 과제를 정리합니다.

> [확인 필요: 고객 가명과 사례 공개 범위. 2026-09-30 기록은 구성 테스트 중·사양 확정 예정 단계이므로, 실제 적용 구성과 운영 전환 완료일은 고객 확인 후 확정합니다. 이 글의 비교 벤치마크는 2026-08-03 수행 결과를 바탕으로 하며, 후속 구성·복구 검토는 별도로 구분합니다.]

## 1. 상품평가 요청이 계산 노드에 도달하기까지

이 플랫폼에서 MongoDB는 계산에 필요한 문서를 HPC에 전달하는 데이터 계층으로 사용됐습니다. 사용자의 평가 요청은 API와 데이터 준비 단계를 거쳐 계산 작업으로 만들어지고, HPC 계산 노드는 MongoDB에서 필요한 데이터를 읽어 병렬 계산을 수행합니다.

```text
평가 요청
  → API·평가 데이터 준비
  → 문서 데이터 계층
  → HPC 병렬 계산
  → 결과 저장·조회
```

> [확인 필요: 공개 가능한 실제 시스템 흐름과 결과 저장 경로.]

업무는 정규 배치로만 구성되지 않았습니다. 업무 시간 동안 들어오는 평가 요청과 필요에 따라 발생하는 시뮬레이션 요청도 처리해야 했습니다. 따라서 하루 평균 작업량을 처리하는 것뿐 아니라, 여러 task가 동시에 시작될 때 데이터 계층이 어떻게 동작하는지도 중요했습니다.

이번 애플리케이션은 **task마다 client를 새로 만들고 짧게 사용한 뒤 폐기하는 방식**이었습니다. 연결을 오래 유지하는 일반적인 웹 애플리케이션과 달리, 연결 수립과 인증이 task 실행 경로에 반복적으로 포함됩니다. 쿼리가 빠르더라도 연결을 제때 만들지 못하면 전체 작업이 지연될 수 있는 구조였습니다.

이 특성 때문에 데이터베이스를 고를 때는 개별 쿼리 지연뿐 아니라 연결 생성률, 동시 연결 수, 실패 후 복구까지 함께 살펴봐야 했습니다.

## 2. 바꾸려던 것은 DB만이 아니라 직접 운영해야 하는 범위였다

기존 환경에서는 MongoDB와 함께 VM, 라우터, standby, 패치, 인증서, 용량 조정을 직접 관리했습니다. 클라우드 전환 과정에서 기존 구성을 Azure VM에 유지하는 방법과, 관리형 서비스로 데이터 계층의 운영 방식을 바꾸는 방법을 검토했습니다.

초기 논의에는 기존 MongoDB의 장애 경험에 따른 이중화 우려와 버전 업그레이드 필요가 포함됐습니다. 한편 관리형 서비스로 바꾸면 OS나 데이터베이스 프로세스를 직접 조정하던 방식도 달라집니다. 구축 일정과 애플리케이션 호환성을 확인하지 않은 채 운영 편의성만으로 선택할 수는 없었습니다.

> [확인 필요: 기존 장애·업그레이드 이슈의 공개 범위와 최종 도입 동기. 장애의 업무 영향과 운영 공수는 고객 확인 전 정량 성과로 서술하지 않습니다.]

### Azure DocumentDB는 어떤 데이터베이스인가

Azure DocumentDB는 오픈소스 [DocumentDB](https://github.com/documentdb/documentdb)를 기반으로 하는 **완전 관리형 MongoDB 호환 문서 데이터베이스**입니다. MongoDB 서버를 Azure에서 대신 실행하는 서비스는 아니며, 별도의 구현으로 MongoDB wire protocol과 BSON을 지원합니다.

이 호환성은 기존 MongoDB 애플리케이션을 검토하는 팀에게 중요한 출발점입니다. MongoDB 드라이버와 도구, 익숙한 문서 모델과 쿼리 사용 방식을 활용하면서 데이터베이스 인프라의 운영 방식을 바꿀 수 있기 때문입니다. 다만 연결 가능 여부와 실제 애플리케이션의 동작 호환성은 구분해 확인해야 합니다.

Microsoft 공식 문서는 **99.03%의 MongoDB 호환성**을 안내합니다. 이 수치는 지원하는 집계·쿼리·프로젝션·업데이트 연산자를 기준으로 산정하며, 명령과 관리 작업은 계산에서 제외합니다. 따라서 모든 애플리케이션이 99.03%의 확률로 수정 없이 이전된다는 의미는 아닙니다. 실제로 사용하는 드라이버, 쿼리, 인덱스, 명령과 운영 도구의 지원 여부를 점검해야 합니다.

관련 범위는 [Azure DocumentDB 개요](https://learn.microsoft.com/en-us/azure/documentdb/overview)와 [MongoDB 쿼리 언어 호환성](https://learn.microsoft.com/en-us/azure/documentdb/compatibility-query-language#compatibility-philosophy)에서 확인할 수 있습니다.

이번 사례에서는 이 호환성을 바탕으로 기존 접근 방식을 유지할 수 있는지 시험하면서, 직접 운영하던 인프라 범위를 줄이는 방향을 검토했습니다.

| 항목 | 자체 관리형 MongoDB | Azure DocumentDB에서의 접근 |
|---|---|---|
| 인프라 운영 | VM, MongoDB 프로세스, 라우터와 standby 등을 직접 구성·관리 | 관리형 클러스터와 HA 설정을 사용하고 기반 인프라 운영은 서비스에 위임 |
| 용량 조정 | VM 증설과 데이터베이스 구성 변경 | 티어와 샤드 구성으로 조정 |
| 애플리케이션 연결 | 토폴로지와 연결 설정을 직접 검토 | global 연결 문자열을 사용하되 DNS·timeout·retry는 검증 |
| 관측과 복구 | 모니터링·백업·복구 절차 구성 | Azure Monitor와 자동 백업을 활용하되 알림·복원 검증·DR 정책은 별도 설계 |

운영 가치의 핵심은 모든 업무가 사라진다는 데 있지 않습니다. **서비스에 위임할 영역과 고객이 계속 판단할 영역을 구분할 수 있다는 점**에 있습니다.

## 3. CPU보다 먼저 확인해야 했던 연결 패턴

제품의 호환성과 관리형 기능만으로 HPC에 적합한지 판단할 수는 없었습니다. 검증에서는 기존 애플리케이션의 연결 패턴을 재현하는 데 초점을 맞췄습니다.

| 검증 항목 | 확인하려던 질문 |
|---|---|
| 애플리케이션 호환성 | 기존 드라이버·쿼리·도구를 어느 범위까지 유지할 수 있는가 |
| 평균 업무 부하 | 필요한 작업량을 안정적으로 처리하는가 |
| 신규 연결 폭주 | 짧은 시간에 연결 요청이 몰리면 어디에서 병목이 발생하는가 |
| 연결 유지 | 많은 연결이 누적된 상태를 유지하고 조회할 수 있는가 |
| 변경과 복구 | 티어 변경 등으로 연결 대상이 바뀔 때 애플리케이션이 복구하는가 |

비교 벤치마크에서는 평균 약 **135 tasks/s**의 부하, 약 **1,210 new connections/s**의 피크형 부하, 약 **3,900 new connections/s**의 한계 탐색 부하를 구분했습니다. 별도로 **12,000개 연결 유지** 시험을 수행했습니다.

> [확인 필요: 위 부하와 실제 운영 패턴의 대응 관계, 업무의 허용 오류율·지연 기준. 각 시나리오는 서로 다른 시험이며, 수치를 하나의 동시 달성 결과로 해석하지 않습니다.]

평균 처리량과 동시 연결 수는 같은 지표가 아닙니다. 많은 연결이 열려 있어도 대부분 대기 상태일 수 있고, 동시 연결 수가 낮더라도 연결을 빠르게 생성·종료하면 handshake와 인증 부하가 커질 수 있습니다. 두 상황을 나눠 봐야 티어와 샤드의 효과도 구분할 수 있습니다.

부하 발생기 자체가 먼저 한계에 도달하지 않는지도 확인했습니다. .NET ThreadPool starvation은 최소 thread 수를 조정해 대응했고, Private Endpoint 환경에서는 인증서 폐기 확인 경로와 DNS 해석을 점검했습니다. 클라이언트에서 발생한 지연을 DB 서버의 성능 한계로 해석하지 않기 위한 과정이었습니다.

시험 구성, 스크립트와 지표 정의는 [기술 문서](hpc-mongodb-to-documentdb-reference.md)에 별도로 정리했습니다.

## 4. 테스트가 알려준 것: 티어, 샤드, 클라이언트는 다른 문제를 풀었다

### 평균 업무 부하에서는 처리량을 유지하고 읽기 중앙값을 낮췄다

평균 약 135 tasks/s 조건에서 Azure DocumentDB와 자체 관리형 MongoDB는 모두 비슷한 처리량을 보였습니다. Azure DocumentDB의 읽기 지연 중앙값은 더 낮았지만, 모든 지연 지표에서 우세한 것은 아니었습니다.

> [확인 필요: 아래 수치의 공개 승인과 원본 결과 대조. DocumentDB는 M80·샤드 2개, 비교 MongoDB는 mongos 4개 구성의 결과이며 최종 운영 환경과 동일한 조건인지는 별도 확인이 필요합니다.]

| 지표 | Azure DocumentDB | 자체 관리형 MongoDB |
|---|---|---|
| 평균 워크로드 처리량 | 134.9 tasks/s | 134.9 tasks/s |
| 평균 워크로드 오류율 | 0.000% | 0.001% |
| 읽기 지연 중앙값 | 27.5 ms | 45.6 ms |
| 평균 워크로드 p99 | 107.8 ms | 67.9 ms |
| 12,000개 연결 유지 시험의 연결 실패율 | 0.2% | 6.1% |
| 연결 유지 시험의 keepalive p99 | 23.3 s | 14.8 s |

읽기 중앙값이 낮다는 사실만으로 전체 작업이 더 빨라졌다고 결론내리지는 않았습니다. 일부 상위 백분위 지연은 MongoDB가 더 낮았으므로, 고객 업무의 timeout과 전체 작업 완료 시간에 미치는 영향도 함께 확인해야 했습니다.

### 평균 부하와 연결 폭주에서는 티어의 의미가 달랐다

시험한 평균 부하에서 M60·M80·M200의 처리량은 **134.7–134.9 tasks/s**로 비슷했습니다. 이 조건에서는 티어를 높여도 처리량 차이가 거의 관측되지 않았습니다. 고객 환경 검토에서도 CPU 성능은 M60 수준에서 여유가 있었다는 점을 확인했습니다.

반면 연결 폭주 시험에서는 다른 결과가 나왔습니다. 샤드 1개에서 M80을 M200으로 변경했을 때 처리량은 **22.0 tasks/s에서 154.7 tasks/s**로 증가했습니다. 같은 티어 변경이라도 부하 유형에 따라 결과가 달랐습니다.

약 3,900 new connections/s의 한계 탐색 조건에서는 server CPU가 **1.2–1.5%**였는데도 오류율이 **72–97%**에 이르렀습니다. 낮은 CPU 사용률만으로 새 연결을 충분히 받아들일 수 있다고 판단할 수 없다는 결과였습니다. 연결 수립·허용 단계의 제약을 시사하지만, 내부 gateway 용량을 직접 측정한 것은 아닙니다.

또한 약 1,210 new connections/s의 단일 샤드 M80 시험에서는 최대 **9,979개 연결**, **191.6 tasks/s**와 함께 **38.8% 오류율**이 관측됐습니다. 연결 수나 처리량만으로 이 구성을 운영에 적합하다고 판정할 수는 없었습니다.

### 샤드 증설의 효과는 실제 데이터 분산과 함께 확인했다

연결 유지 시험에서는 샤드 1개가 약 11,000개 연결에서 정체했고, 티어만 올리는 것으로 한계가 해소되지 않았습니다. 데이터를 샤드 2개에 분산한 구성에서는 시험 상한인 **12,000개 연결**에 도달했습니다. 연결 실패율은 약 **37–38%에서 0.1–1.0%**로, keepalive p99는 **114–139초에서 23–34초**로 낮아졌습니다.

이는 해당 시험 조건의 관측 결과입니다. 12,000개가 제품의 최대 연결 수라는 의미도, 모든 반복 시험에서 동일하게 달성했다는 의미도 아닙니다.

샤드를 추가하는 것과 데이터를 분산하는 것도 별개였습니다. 샤드 2개를 프로비저닝했지만 데이터가 한 샤드에 남아 있던 경우가 있어, collection 샤딩과 데이터 적재 후 chunk metadata와 query explain으로 분산을 확인했습니다.

이 검증을 통해 얻은 판단은 단순했습니다. **평균 처리량, 연결 생성, 연결 유지는 나눠 측정하고, 티어와 샤드는 해당 병목에 맞춰 선택해야 합니다.**

## 5. 선정한 구성과, 관리형이어도 남아 있는 설계

### M80·샤드 2개·HA 구성

운영계로 선정한 구성은 M80·샤드 2개·HA입니다. M80은 샤드당 **32 vCore·128 GiB RAM**을 제공하므로, 주 샤드 2개에는 합계 **64 vCore·256 GiB RAM**이 할당됩니다. HA를 활성화하면 각 주 샤드에 같은 사양의 standby 샤드가 추가됩니다. 상세 사양은 [compute와 storage 문서](https://learn.microsoft.com/en-us/azure/documentdb/compute-storage)를 참고할 수 있습니다.

M60 수준에서도 CPU 여유가 있었으므로, M80 선정은 더 높은 CPU 성능이 반드시 필요했다는 의미는 아닙니다. 이번 기술 검토에서 중요한 것은 CPU 증설 자체보다 연결 유지 특성, 데이터 분산과 장애 대응을 함께 확인하는 일이었습니다.

단일 샤드보다 샤드 2개를 선택한 것은 이 애플리케이션의 연결 패턴과 연결 유지 시험을 고려한 판단이었습니다. 이를 모든 MongoDB 호환 워크로드에 적용되는 권장 구성으로 일반화하지는 않습니다.

> [확인 필요: 선정 구성의 실제 적용 상태, HA를 포함한 최종 구성의 검증 범위와 고객 승인.]

### HA와 연결 문자열만으로 애플리케이션 무중단이 완성되지는 않는다

Azure DocumentDB의 HA는 각 주 샤드와 standby 사이에 동기 복제를 사용합니다. 서비스는 주 샤드 장애를 감지하면 standby로 전환하며, 연결 문자열은 유지됩니다. 공식 문서는 HA 활성화 시 샤드별 **99.99% 가용성 SLA**를 안내합니다. 이는 적용 조건이 있는 서비스 수준 약정이며, 애플리케이션의 모든 요청이 지연이나 실패 없이 완료된다는 의미는 아닙니다.

후속 티어 변경 시험에서는 연결 설정의 중요성을 확인했습니다. 특정 노드 호스트네임으로 고정하던 방식을 제거하고 global SRV 연결을 드라이버에 그대로 전달했습니다. HA를 활성화하고, server selection timeout을 30초로 조정하며 읽기·쓰기 재시도를 사용했습니다.

비피크 **50 RPS** 조건에서 M30↔M60, M60↔M200, M200↔M30 전환을 시험한 후속 기록에는 읽기 오류 0건, 쓰기 오류 **0.02% 미만**, 완전 단절 시간 **6.1초·1.6초·2.5초**가 기록됐습니다.

> [확인 필요: 2026-08-30 후속 시험의 원본 로그, 각 단절 시간의 시나리오 대응과 지표 정의. 연결 설정과 시험 부하를 함께 변경했으므로 개선을 특정 설정 하나의 효과로 해석하지 않습니다. 이 결과는 피크 부하에서의 무중단 보장이 아닙니다.]

Global endpoint는 클러스터의 논리적 연결 지점이고, Private Endpoint는 사설 네트워크로 접근하는 경로입니다. 둘은 대체 관계가 아니므로 함께 구성할 수 있습니다. 이때 seed hostname과 SRV target hostname이 모두 사설 경로로 해석되는지도 점검해야 합니다.

HA의 서비스 동작은 [고가용성 문서](https://learn.microsoft.com/en-us/azure/documentdb/high-availability)를 참고하고, 실제 애플리케이션의 복구는 별도 시험으로 확인하는 접근이 필요합니다.

### 자동 백업과 데이터 보관 정책은 구분한다

M80과 같은 활성 비버스터블 클러스터의 자동 백업은 35일간 보존되며, PITR은 새 클러스터를 생성하는 방식으로 복원합니다. 자동 백업을 사용하더라도 복원 후 연결 경로와 보안·네트워크·HA 설정, 애플리케이션의 재접속을 확인해야 합니다. 자동 백업만으로 대규모 장애에 대한 DR 계획이 완성되지는 않습니다.

이 프로젝트에서도 최근 데이터와 보관 데이터를 어떻게 구분할지, 기존 mongodump 기반 도구를 활용할지, 장기 보관 데이터를 별도 저장소로 옮길지 검토했습니다. 이는 서비스가 대신 결정할 수 없는 업무 정책입니다.

> [확인 필요: 실제 채택한 데이터 보관·아카이빙 구성과 복원 시험 결과. 검토안을 구현 완료 구성으로 소개하지 않습니다.]

복원 범위와 조건은 [백업 및 복원 문서](https://learn.microsoft.com/en-us/azure/documentdb/how-to-restore-cluster)에서 확인할 수 있습니다.

## 6. 고객 환경에서 확인한 변화와 최종 확인할 결과

벤치마크 이후에는 고객 애플리케이션에서 작업을 실행하며 구성을 검토했습니다. 2026-09-30 기록에는 운영계 M80, 개발계 M60으로 구성을 확정할 예정이며, 운영 기준 Job 수행 후 **Task 기준 57만 건까지 진행했고 당시 문제를 파악하지 못했다**는 내용이 남아 있습니다.

이 기록은 고객 환경에서 검증이 진행됐다는 근거입니다. 다만 측정된 오류율이나 전체 처리 시간이 함께 제시되지 않았으므로, 57만 Task가 모두 무오류로 완료됐거나 운영 안정화가 끝났다는 뜻으로 확대하지 않습니다.

전체 처리 시간이 줄었다는 점도 확인하고 있습니다. 공개 원고에서는 동일한 작업량과 비교 조건을 기준으로 감소 폭을 확정할 예정입니다. Azure Batch와 애플리케이션을 포함한 플랫폼 변화의 결과이므로, 분리 검증 없이 Azure DocumentDB 단독 효과로 귀속하지는 않습니다.

| 가치 축 | 현재 정리할 수 있는 변화 | 공개 전 확정할 내용 |
|---|---|---|
| 업무 처리 | 전체 처리 시간 감소 | [확인 필요: 동일 작업량 기준 전환 전후 시간, 비교 환경과 개선 폭] |
| 안정성 | 평균·연결 폭주·연결 유지와 변경·복구를 구분해 검증 | [확인 필요: 최종 HA 구성의 피크 성공률, 재처리 건수, 운영 관측 기간] |
| 운영 효율 | 직접 관리하는 DB 인프라 범위를 줄이는 방향으로 전환 | [확인 필요: 실제로 줄어든 구성·점검 업무와 고객의 평가] |

구성 편의성에 대한 긍정적인 고객 피드백도 있었지만, 직접 인용은 발언자와 문구를 확인한 뒤 반영합니다. 운영 공수 절감이나 장애 감소 역시 별도 측정 없이 성과로 단정하지 않습니다.

## 7. 이번 전환에서 얻은 판단 기준

이번 사례에서 Azure DocumentDB의 가치는 MongoDB 호환 인터페이스를 활용하면서, 데이터 계층을 직접 구성·운영하던 방식에서 관리형 서비스의 구성과 정책을 선택하는 방식으로 전환할 수 있다는 점에 있었습니다. 그 가능성을 실제 워크로드로 확인하는 과정이 제품 기능 설명만큼 중요했습니다.

세 가지 판단 기준이 남았습니다.

- **안정성:** 평균 쿼리 성능뿐 아니라 연결 폭주, 연결 유지와 복구 경로까지 검증해야 합니다. CPU가 낮다는 이유만으로 전체 시스템에 여유가 있다고 판단하지 않습니다.
- **운영 효율:** HA와 자동 백업 같은 서비스 기능을 활용하되, 알림·연결 설정·보관·복구 정책에 대한 고객의 책임은 분명히 해야 합니다.
- **확장성:** 티어와 샤드는 같은 문제를 해결하지 않습니다. 부하 유형을 나눠 측정하고, 데이터가 실제로 분산됐는지 확인한 뒤 구성을 판단해야 합니다.

다음 단계는 최종 운영 구성의 지표를 기준으로 처리 시간과 안정성을 확인하고, 장애·복원 절차와 알림 기준을 정리하는 것입니다. [확인 필요: 고객과 합의한 실제 후속 계획.]

비슷한 전환을 검토하는 팀이라면 다음 항목부터 확인할 수 있습니다.

- [ ] 사용하는 MongoDB 드라이버·쿼리·인덱스·명령의 호환 범위를 확인했는가?
- [ ] 평균 처리량, 신규 연결 생성률, 동시 연결 유지량을 나눠 시험했는가?
- [ ] 부하 발생기의 thread·CPU·인증서·DNS 병목을 배제했는가?
- [ ] 샤드 추가 후 실제 데이터 분산을 확인했는가?
- [ ] 연결 경로·timeout·retry를 포함해 변경과 복구를 시험했는가?
- [ ] 개별 DB 지연과 전체 업무 완료 시간을 구분해 비교했는가?
- [ ] HA, 백업, 장기 보관과 DR의 책임 및 검증 범위를 구분했는가?

재현 구성과 상세 측정 방법은 [기술 문서](hpc-mongodb-to-documentdb-reference.md)에 정리했습니다.
